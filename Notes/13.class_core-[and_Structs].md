# C++ Classes and Structs

 Classes and structs are fundamental C++ tools for creating **user-defined types**: types that combine related data and, when appropriate, the operations that work on that data.

 The central idea is simple:

 > **A class or struct lets you define your own type by grouping data and functionality together.**

---

 ## 1\. What Is a Class?

 A **class** is a user-defined type that can contain:

 - **Data** — variables that represent the object's state.
- **Functions** — functions that operate on that state.

 For example, suppose a game needs to represent a player.

 Without a class, you might have:

```
int playerX;
int playerY;
int playerSpeed;
```

 And a function might need all of those values:

```
void Move(int& x, int& y, int speed);
```

 As the program grows, this becomes difficult to manage. A player may eventually have:

 - position
- speed
- health
- name
- graphics
- input handling
- movement functionality

 A class allows these related pieces to be grouped together:

```
class Player
{
public:
    int x;
    int y;
    int speed;

    void Move(int xa, int ya)
    {
        x += xa;
        y += ya;
    }
};
```

 Now the player is a single type:

```
Player player;
```

 and its functionality belongs naturally to the object:

```
player.Move(1, -1);
```

 ### Important idea

 A class does not give the computer some fundamentally new capability that could not be implemented another way. C++ could represent the same underlying information using separate variables and functions.

 The major benefit is **organization, abstraction, and control over how that data and functionality are used**.

---

 # 2\. Why Classes Are Useful

 Consider a program with two players.

 Without a class:

```
int player1X;
int player1Y;
int player1Speed;

int player2X;
int player2Y;
int player2Speed;
```

 You could easily end up with:

```
move(player1X, player1Y, player1Speed);
move(player2X, player2Y, player2Speed);
```

 The relationship between the variables is implicit: you have to remember that `player1X`, `player1Y`, and `player1Speed` all belong to the same player.

 With a class:

```
Player player1;
Player player2;
```

 Each object automatically contains its own state:

```
player1.Move(1, 0);
player2.Move(-1, 0);
```

 The class therefore gives the program a meaningful abstraction:

```
Player
 ├── position
 ├── speed
 └── movement functionality
```

 Instead of thinking about many unrelated variables, you can think in terms of **Player objects**.

---

 # 3\. Classes and Objects

 Two terms are particularly important:

 - **Class** — the type/definition.
- **Object** — an actual instance of that type.

 A useful analogy is a blueprint.

```
Class
  ↓
Blueprint for a Player

Objects
  ↓
player1
player2
player3
```

 For example:

```
class Player
{
public:
    int x;
    int y;
};
```

 This defines the type `Player`.

 It does not, by itself, create a particular player object.

 You can then create objects:

```
Player player1;
Player player2;
```

 Now `player1` and `player2` are two separate objects.

 Each object has its own `x` and `y`:

```
player1.x = 10;
player2.x = 100;
```

 Changing `player1.x` does not change `player2.x`.

 ### Terminology

 **Object** and **instance** are often used interchangeably in this context.

 An instance is a particular object created from a class.

---

 # 4\. Classes Are User-Defined Types

 C++ already provides built-in types:

```
int
float
double
char
bool
```

 You can define your own type:

```
class Player
{
    // ...
};
```

 `Player` is now a type.

 That means you can write:

```
Player player1;
Player player2;
Player player3;
```

 This is similar conceptually to:

```
int score1;
int score2;
int score3;
```

 except `Player` can contain multiple pieces of related state and functionality.

 This is one of the most important reasons classes are powerful:

 > **You can model concepts in your program as actual types.**

---

 # 5\. Basic Class Syntax

 A class is declared using the `class` keyword:

```
class Player
{
    int x;
    int y;
};
```

 Notice the semicolon after the closing brace:

```
};
```

 ### The semicolon is required

 This is correct:

```
class Player
{
};
```

 This is incorrect:

```
class Player
{
}
```

 The class declaration is a declaration, and the semicolon terminates it.

---

 # 6\. Member Variables

 A variable declared inside a class is called a **member variable** or **data member**.

 Example:

```
class Player
{
public:
    int x;
    int y;
    int speed;
};
```

 Here:

```
x
y
speed
```

 are member variables.

 They represent the **state** of a `Player` object.

 For example:

```
Player player;

player.x = 10;
player.y = 20;
player.speed = 5;
```

 The object's state is now approximately:

```
player
 ├── x     = 10
 ├── y     = 20
 └── speed = 5
```

 ### Object state

 The **state of an object** means the values stored in its member variables at a particular point in time.

 If:

```
player.x = 10;
player.y = 20;
```

 then the player's position is part of its current state.

 A member function can change that state:

```
player.Move(5, 0);
```

 Afterward:

```
x = 15
y = 20
```

---

 # 7\. Member Functions / Methods

 A function declared inside a class is called a **member function**.

 The term **method** is also commonly used.

 Example:

```
class Player
{
public:
    int x;
    int y;

    void Move(int xa, int ya)
    {
        x += xa;
        y += ya;
    }
};
```

 `Move()` is a member function.

 It can directly access the object's member variables:

```
x += xa;
y += ya;
```

 There is no need to pass `x` and `y` as parameters.

 You use the function through an object:

```
Player player;

player.Move(1, -1);
```

 The dot operator:

```
.
```

 is used to access members of an object.

---

 # 8\. Why Member Functions Simplify Code

 Without a member function, you might have something like:

```
void Move(Player& player, int xa, int ya)
{
    player.x += xa;
    player.y += ya;
}
```

 Usage:

```
Move(player, 1, -1);
```

 The function has to be told which `Player` it should modify.

 With a member function:

```
class Player
{
public:
    int x;
    int y;

    void Move(int xa, int ya)
    {
        x += xa;
        y += ya;
    }
};
```

 Usage becomes:

```
player.Move(1, -1);
```

 Conceptually, the member function operates on the particular object through which it was called.

 This is a major benefit of putting related functionality inside the type it belongs to.

---

 # 9\. `public` and `private`

 C++ allows you to control who can access members of a class.

 The two most important access specifiers are:

```
public:
private:
```

 ## `public`

 A public member can be accessed by code outside the class, subject to the usual language rules.

 Example:

```
class Player
{
public:
    int x;
};
```

 Now:

```
Player player;
player.x = 10;
```

 is allowed.

---

 ## `private`

 A private member cannot normally be accessed directly by unrelated outside code.

```
class Player
{
private:
    int x;
};
```

 This is not allowed:

```
Player player;
player.x = 10;   // Error
```

 The class itself can access its private members:

```
class Player
{
private:
    int x;

public:
    void SetX(int value)
    {
        x = value;
    }
};
```

 Now outside code uses the public interface:

```
Player player;
player.SetX(10);
```

---

 # 10\. Default Visibility

 There is an important difference between `class` and `struct`.

 For a **class**:

 > Members are `private` by default.

 Therefore:

```
class Player
{
    int x;
};
```

 is effectively:

```
class Player
{
private:
    int x;
};
```

 For a **struct**:

 > Members are `public` by default.

 Therefore:

```
struct Player
{
    int x;
};
```

 is effectively:

```
struct Player
{
public:
    int x;
};
```

 This is a real C++ language rule.

---

 # 11\. Encapsulation

 **Encapsulation** means controlling access to an object's internal state and exposing an appropriate interface for interacting with it.

 For example:

```
class BankAccount
{
private:
    double balance;

public:
    void Deposit(double amount)
    {
        balance += amount;
    }
};
```

 Outside code cannot directly modify:

```
account.balance
```

 Instead, it interacts through:

```
account.Deposit(100);
```

 The class controls how its internal state is modified.

 This allows the implementation to change without necessarily changing the code that uses the class.

 ### Why this matters

 Suppose the class later needs validation:

```
void Deposit(double amount)
{
    if (amount > 0)
        balance += amount;
}
```

 Code using the class can continue calling:

```
account.Deposit(100);
```

 The details of how the operation is implemented remain inside the class.

---

 # 12\. Class Interface and API

 The **interface** of a class is the set of operations and members that users of the class are intended to interact with.

 For example:

```
class Log
{
public:
    void SetLevel(int level);
    void Error(const char* message);
    void Warn(const char* message);
    void Info(const char* message);

private:
    int m_LogLevel;
};
```

 The public functions form much of the class's interface.

 A programmer using the class does not need to know how logging is internally implemented.

 They simply need to know:

```
Log log;

log.SetLevel(...);
log.Warn(...);
```

 The **API (Application Programming Interface)** is the interface through which other code interacts with a component.

 For a class, the public interface is an important part of its API.

---

 # 13\. Class vs Struct

 In C++, `class` and `struct` are much more similar than beginners sometimes expect.

 Both can contain:

 - member variables
- member functions
- constructors
- destructors
- access specifiers
- static members
- nested types
- operators
- inheritance
- templates
- and much more

 The fundamental technical difference in their declaration is their **default access control**.

 | Feature | `class` | `struct` |
| --- | --- | --- |
| Default member access | `private` | `public` |
| Can contain variables | Yes | Yes |
| Can contain functions | Yes | Yes |
| Can have constructors | Yes | Yes |
| Can use inheritance | Yes | Yes |
| Can have private members | Yes | Yes |
| Can have public members | Yes | Yes |

There is also a related difference involving **default inheritance access**, discussed below.

---

 # 14\. `class` and `struct` Are Not Completely Different Types

 This is valid:

```
struct Player
{
    int x;
    int y;

    void Move()
    {
        x++;
    }
};
```

 You could change it to:

```
class Player
{
public:
    int x;
    int y;

    void Move()
    {
        x++;
    }
};
```

 The resulting type has the same member-access behavior.

 The difference is that `struct` begins with public access automatically, while `class` begins with private access.

 This is why the following two definitions have equivalent access behavior:

```
struct Vec2
{
    float x;
    float y;
};
```

 and:

```
class Vec2
{
public:
    float x;
    float y;
};
```

---

 # 15\. Why Does C++ Have `struct`?

 C++ was designed as an extension of C.

 C already had `struct`.

 C++ retained the concept for compatibility and familiarity with C-style code.

 C++ then added classes and object-oriented features while retaining `struct`.

 Therefore, C++ ended up with two closely related ways of declaring user-defined types.

 The distinction became useful as a matter of **convention and intent**, even though the language capabilities overlap heavily.

---

 # 16\. When to Use a Struct vs a Class

 This part should be distinguished from the language rules.

 C++ does **not** have a rule saying:

 > "Structs are only for data."

 Nor does C++ prohibit inheritance with structs.

 A `struct` can absolutely have:

```
private:
```

 and can participate in inheritance.

 For example:

```
struct Animal
{
    virtual void Speak() {}
};
```

 is perfectly valid C++.

 Therefore, recommendations about when to use `struct` versus `class` are largely **design conventions**, not technical restrictions.

 ### A common convention

 A useful convention is:

 **Use a `struct` when the type primarily represents simple, openly accessible data.**

 Example:

```
struct Vec2
{
    float x;
    float y;
};
```

 This communicates:

 > "This type is primarily a collection of values."

 A `struct` can still contain functions:

```
struct Vec2
{
    float x;
    float y;

    void Add(const Vec2& other)
    {
        x += other.x;
        y += other.y;
    }
};
```

 That is completely valid.

---

 ## Use a class when encapsulation and behavior are central

 For a more complex object:

```
class Player
{
private:
    int health;

public:
    void TakeDamage(int amount);
    void Move(float x, float y);
};
```

 The private state and public operations communicate that the object has controlled behavior and an internal implementation.

 ### The Cherno's convention

 The practical convention presented in the material is roughly:

 | Prefer | Typical purpose |
| --- | --- |
| `struct` | Simple data-oriented types |
| `class` | More complex objects with substantial functionality |
| `class` | Types forming inheritance hierarchies |

This is a **style guideline**, not a C++ language requirement.

 The statement "never use inheritance with structs" should therefore be understood as a design rule of thumb rather than a language rule.

---

 # 17\. Default Inheritance Access

 There is one additional technical difference worth knowing.

 For a `class`:

```
class Derived : Base
{
};
```

 inheritance is **private by default**.

 For a `struct`:

```
struct Derived : Base
{
};
```

 inheritance is **public by default**.

 So these are equivalent:

```
class Derived : private Base
{
};
```

 and:

```
struct Derived : public Base
{
};
```

 This is separate from member visibility, but follows the same general `class` vs `struct` default-access distinction.

 You can always specify it explicitly:

```
class Derived : public Base
{
};
```

---

 # 18\. Designing a Class

 A useful class should represent a meaningful concept.

 For example:

```
class Player
{
    // Player-related state and functionality
};
```

 rather than creating a class simply because the language allows it.

 A class should answer questions such as:

 - What does this object represent?
- What state does it need?
- What operations should it support?
- Which details should users be able to access?
- Which details should remain internal?

---

 # 19\. Design the API Around How the Class Is Used

 A useful design principle is to think about how you want the class to be used.

 For a logging class, you might want client code to look like:

```
Log log;

log.SetLevel(...);
log.Warn("Something happened.");
```

 This immediately tells you something about the API:

 - There should be a `Log` type.
- It should have a `SetLevel()` function.
- It should have a `Warn()` function.
- The internal log level needs to be stored somewhere.

 Only after establishing the desired usage do you implement the internals.

 This helps prevent the implementation from dictating an awkward interface.

---

 # 20\. Member Variables and Naming

 Member variables store an object's state.

 For example:

```
class Log
{
private:
    int m_LogLevel;
};
```

 The name:

```
m_LogLevel
```

 uses the `m_` prefix convention.

 The purpose is to make it immediately obvious that this is a **member variable**.

 For example:

```
void SetLevel(int level)
{
    m_LogLevel = level;
}
```

 Here:

```
level
```

 is a local parameter, while:

```
m_LogLevel
```

 is a member variable.

 ### Important distinction

 The `m_` naming convention is **not a C++ language requirement**.

 These are all legal:

```
int m_LogLevel;
int logLevel;
int log_level;
int level_;
```

 The `m_` convention is simply a style choice.

---

 # 21\. Constants Inside a Class

 The logger needs different levels.

 Instead of writing:

```
log.SetLevel(1);
```

 we want readable names:

```
log.SetLevel(log.LogLevelWarning);
```

 The names communicate what the values mean.

 The original introductory implementation uses:

```
const int LogLevelError = 0;
const int LogLevelWarning = 1;
const int LogLevelInfo = 2;
```

 This demonstrates an important principle:

 > **Meaningful names are preferable to unexplained magic numbers.**

 Modern C++ would generally use an `enum` or `enum class` for this particular purpose, but the integer constants are useful for understanding the basic class concepts being demonstrated.

---

 # 22\. The Logger Example

 The logger is a useful example because it demonstrates nearly everything introduced above.

 We want a type that:

 - represents a logger
- stores its current log level
- provides public operations
- keeps its internal state private
- allows users to change the level
- prints messages according to that level

 The desired usage is:

```
Log log;

log.SetLevel(log.LogLevelWarning);

log.Error("Something went wrong.");
log.Warn("Be careful.");
log.Info("Everything is running.");
```

 The user of the class does not need to manipulate the internal `m_LogLevel` directly.

---

 # 23\. Complete Program

```
#include <iostream>

class Log
{
public:
    // Log level constants
    const int LogLevelError = 0;
    const int LogLevelWarning = 1;
    const int LogLevelInfo = 2;

private:
    // Internal state of the logger
    int m_LogLevel = LogLevelInfo;

public:
    // Change the current log level
    void SetLevel(int level)
    {
        m_LogLevel = level;
    }

    // Print an error message
    void Error(const char* message)
    {
        if (m_LogLevel >= LogLevelError)
            std::cout << "[ERROR]: " << message << std::endl;
    }

    // Print a warning message
    void Warn(const char* message)
    {
        if (m_LogLevel >= LogLevelWarning)
            std::cout << "[WARNING]: " << message << std::endl;
    }

    // Print an informational message
    void Info(const char* message)
    {
        if (m_LogLevel >= LogLevelInfo)
            std::cout << "[INFO]: " << message << std::endl;
    }
};

int main()
{
    Log log;

    log.SetLevel(log.LogLevelWarning);

    log.Error("Something went wrong.");
    log.Warn("Something might be wrong.");
    log.Info("Everything is running normally.");

    return 0;
}
```

 With the level set to `LogLevelWarning`, the output is:

```
[ERROR]: Something went wrong.
[WARNING]: Something might be wrong.
```

 The informational message is not printed.

 ## 24.1 Including `<iostream>`

```
#include <iostream>
```

 This provides the standard input/output facilities needed for:

```
std::cout
std::endl
```

---

 ## 24.2 Defining the class

```
class Log
{
```

 This declares a new type called `Log`.

 We can create objects of this type:

```
Log log;
```

 The class itself is the definition; `log` is an object/instance.

---

 ## 24.3 Public log-level constants

```
public:
    const int LogLevelError = 0;
    const int LogLevelWarning = 1;
    const int LogLevelInfo = 2;
```

 These members are public, so code outside the class can access them.

 For example:

```
log.LogLevelWarning
```

 They give meaningful names to the numeric levels.

 Conceptually:

```
LogLevelError   → 0
LogLevelWarning → 1
LogLevelInfo    → 2
```

 # 25\. The Private Member Variable

```
private:
    int m_LogLevel = LogLevelInfo;
```

 This is the logger's internal state.

 The variable records the currently selected logging level.

 It is private, so outside code cannot do:

```
log.m_LogLevel = 1;   // Error
```

 Instead, the class provides:

```
log.SetLevel(...);
```

 This is encapsulation.

---

 # 26\. `SetLevel()`

```
void SetLevel(int level)
{
    m_LogLevel = level;
}
```

 This is a member function.

 It modifies the object's state.

 Suppose:

```
Log log;
```

 Initially:

```
m_LogLevel = LogLevelInfo
```

 Then:

```
log.SetLevel(log.LogLevelWarning);
```

 changes the state to:

```
m_LogLevel = LogLevelWarning
```

 The object has changed state because a member function modified its member variable.

---

 # 27\. The `Error()` Function

```
void Error(const char* message)
{
    if (m_LogLevel >= LogLevelError)
        std::cout << "[ERROR]: " << message << std::endl;
}
```

 This function:

 1. Receives a message.
2. Checks the object's current log level.
3. Prints the message if the level permits it.

 The important point is that it can directly access:

```
m_LogLevel
```

 because it is a member function of `Log`.

---

 # 28\. The `Warn()` Function

```
void Warn(const char* message)
{
    if (m_LogLevel >= LogLevelWarning)
        std::cout << "[WARNING]: " << message << std::endl;
}
```

 The same principle applies.

 If:

```
m_LogLevel == LogLevelWarning
```

 then:

```
m_LogLevel >= LogLevelWarning
```

 is true.

 Therefore warnings are printed.

---

 # 29\. The `Info()` Function

```
void Info(const char* message)
{
    if (m_LogLevel >= LogLevelInfo)
        std::cout << "[INFO]: " << message << std::endl;
}
```

 If the logger is set to:

```
LogLevelWarning
```

 then:

```
1 >= 2
```

 is false.

 Therefore informational messages are suppressed.

---

 # 30\. Understanding the Log-Level System

 The levels are ordered:

```
Error   = 0
Warning = 1
Info    = 2
```

 The implementation uses:

```
if (m_LogLevel >= requiredLevel)
```

 This means selecting a lower level allows more severe messages to pass.

 For example, at `Info`:

```
Error   → printed
Warning → printed
Info    → printed
```

 At `Warning`:

```
Error   → printed
Warning → printed
Info    → suppressed
```

 At `Error`:

```
Error   → printed
Warning → suppressed
Info    → suppressed
```

 The numeric representation is simply the mechanism used by this introductory implementation.

 # 31\. API vs Implementation

 One of the most important class-design concepts is the distinction between **what a class exposes** and **how it works internally**.

 For `Log`, client code might only need to know:

```
Log log;

log.SetLevel(log.LogLevelWarning);
log.Warn("Be careful.");
```

 The client does not need to know that the logger internally stores:

```
int m_LogLevel;
```

 or that it uses:

```
std::cout
```

 to print the message.

 This separation allows implementation details to change without necessarily changing the code that uses the class.

 Conceptually:

```
             Log API
                │
        ┌───────┴────────┐
        │                │
   SetLevel()          Warn()
        │                │
        └───────┬────────┘
                │
         Internal state
         m_LogLevel
                │
         Implementation
```

 # 32\. Public vs Private: A Practical Mental Model

 A useful beginner-friendly way to think about access control is:

 ### Public

 > "This is part of the interface that outside code may use."

 ### Private

 > "This is an implementation detail controlled by the class."

 For example:

```
class Player
{
private:
    int health;

public:
    void TakeDamage(int amount);
    int GetHealth() const;
};
```

 A user of `Player` interacts with:

```
player.TakeDamage(10);
player.GetHealth();
```

 rather than manipulating:

```
player.health
```

 directly.

 This gives the class control over its own state.

---

 # 33\. Classes Do Not Automatically Mean "Everything Must Be Private"

 Encapsulation does not mean every member must always be private.

 C++ allows you to choose the appropriate access level.

 For example, a simple data type can reasonably use public members:

```
struct Vec2
{
    float x;
    float y;
};
```

 A more controlled abstraction might use private members:

```
class Player
{
private:
    float x;
    float y;

public:
    void Move(float dx, float dy);
};
```

 The right design depends on what the type represents and how it should be used.

---

 # 34\. One Object Has Its Own State

 Consider:

```
Log log1;
Log log2;
```

 These are two separate objects.

 Each object has its own:

```
m_LogLevel
```

 Conceptually:

```
log1
 └── m_LogLevel = Warning

log2
 └── m_LogLevel = Info
```

 Changing one does not automatically change the other:

```
log1.SetLevel(log1.LogLevelWarning);
```

 does not change `log2`'s state.

 This is an important consequence of creating objects from a class.

---

 # 35\. A Class Can Be Used to Create Many Objects

 The class is the type definition:

```
class Player
{
    // ...
};
```

 From it, you can create multiple objects:

```
Player player1;
Player player2;
Player player3;
```

 All three objects have the structure and functionality defined by `Player`, but each object has its own instance-specific state.

 This is one reason classes are useful for representing entities such as:

```
Player
Enemy
Camera
Window
Logger
File
AudioDevice
```

 # 36\. Important Language Rules vs Design Conventions

 It is useful to keep these categories separate.

 ### C++ language rules

 These are part of the language itself:

 - A `class` is a user-defined type.
- A `struct` is also a user-defined type.
- Class members are private by default.
- Struct members are public by default.
- Class inheritance is private by default.
- Struct inheritance is public by default.
- Both classes and structs can have member functions.
- Both can have private/public members.
- Both can participate in inheritance.
- A class declaration requires its terminating semicolon.

 ### Design conventions

 These are choices made by programmers or teams:

 - Prefix private member variables with `m_`.
- Prefer structs for simple data-oriented types.
- Prefer classes for complex abstractions.
- Prefer classes for inheritance hierarchies.
- Keep implementation details private.
- Design APIs around how users should interact with the type.

 These conventions can be useful without being language requirements.

 # 37\. The Introductory Logger Is Deliberately Simple

 The logger demonstrates the basic mechanics of classes:

```
class
 ↓
public/private
 ↓
member variables
 ↓
member functions
 ↓
object creation
 ↓
object state
 ↓
API usage
```

 It is not intended to represent ideal production-level C++.

 For example, modern C++ would commonly improve aspects such as:

 - log-level representation
- constant definitions
- API design
- validation
- string handling
- static/shared configuration where appropriate
- separation of declaration and implementation

 Those improvements introduce additional C++ concepts.

 The important point is that the simple version makes the underlying class mechanics easy to see.

 # 38\. A More General Example of Class Design

 The same principles apply to many types.

 Suppose we need a `Player`.

 A poor design might expose everything:

```
class Player
{
public:
    int health;
    float x;
    float y;
    float speed;
};
```

 Outside code can freely modify everything:

```
player.health = -500;
player.speed = -1000;
```

 A more encapsulated design might be:

```
class Player
{
private:
    int m_Health = 100;
    float m_X = 0.0f;
    float m_Y = 0.0f;

public:
    void Move(float dx, float dy)
    {
        m_X += dx;
        m_Y += dy;
    }

    void TakeDamage(int amount)
    {
        if (amount > 0)
            m_Health -= amount;
    }

    int GetHealth() const
    {
        return m_Health;
    }
};
```

 Now the class controls how its state changes.

 This is the broader idea behind encapsulation.

 # 39\. The Dot Operator

 Objects access their members using `.`.

 For example:

```
Log log;

log.SetLevel(log.LogLevelWarning);
log.Warn("Warning!");
```

 Here:

```
log.SetLevel(...)
```

 calls a member function.

 And:

```
log.LogLevelWarning
```

 accesses a member.

 The same syntax applies to public data members:

```
Vec2 position;

position.x = 10;
position.y = 20;
```

 # 40\. Class Declaration vs Object Creation

 These two operations should not be confused.

 ### Defining the class

```
class Player
{
public:
    int x;
};
```

 This defines a type.

 ### Creating an object

```
Player player;
```

 This creates an object of that type.

 Think:

```
class Player
     ↓
defines the type

Player player
     ↓
creates an object
```

 # 41\. Classes as a Combination of Data and Behavior

 The central idea can be summarized as:

```
             Class
               │
       ┌───────┴────────┐
       │                │
     Data            Behavior
       │                │
member variables    member functions
       │                │
       └───────┬────────┘
               │
             Object
               │
          has its own
             state
```

 For a `Player`:

```
Player
 ├── x
 ├── y
 ├── speed
 └── Move()
```

 For a `Log`:

```
Log
 ├── m_LogLevel
 ├── SetLevel()
 ├── Error()
 ├── Warn()
 └── Info()
```

 The class groups things that logically belong together.

 # 42\. Important Takeaways

 1. **A class is a user-defined type.**
2. **A class can group data and functionality together.**
3. **An object is an instance of a class.**
4. **Each object has its own instance state.**
5. **Member variables store an object's state.**
6. **Member functions/methods operate on the object's state.**
7. **`public` members form part of the interface available to outside code.**
8. **`private` members are implementation details normally inaccessible directly from outside code.**
9. **Encapsulation means controlling access to internal state through an interface.**
10. **A class's API describes how other code interacts with it.**
11. **A `class` defaults to private member access.**
12. **A `struct` defaults to public member access.**
13. **Both classes and structs can have functions, private members, constructors, inheritance, and other C++ features.**
14. **The main technical distinction between `class` and `struct` is their default access rules, including default inheritance access.**
15. **Using structs for simple data and classes for complex, encapsulated objects is a convention, not a language requirement.**
16. **The `m_` prefix for member variables is a naming convention, not a C++ rule.**
17. **Meaningful named constants are preferable to unexplained magic numbers.**
18. **A good class exposes a useful interface while hiding unnecessary implementation details.**
19. **The Logger example demonstrates the complete basic relationship:**

```
class → object → state → member functions → API
```

 20. The most useful mental model is:

```
Class
= definition of a type

Object
= actual instance of that type

Member variables
= object's state

Member functions
= operations on that state

Public
= accessible interface

Private
= controlled internal implementation
```

 At its core, C++ class design is about creating **meaningful types whose state and behavior belong together**, while controlling how the rest of the program interacts with them.
