Video: **“How to DEBUG C++ in VISUAL STUDIO”**

> **Note:** The original video demonstrates debugging with Visual Studio/MSVC. Since I use Linux, the concepts are kept, but Visual Studio-specific controls and MSVC implementation details are separated from the Linux/GDB equivalents.

---

## 1. What Is Debugging?

**Debugging** is the process of finding and fixing bugs in a program.

A bug can come from:

* incorrect logic
* incorrect assumptions
* unexpected variable values
* incorrect memory usage
* incorrect program state
* incorrect interaction between different parts of the program

For example:

```cpp
int a = 5;
int b = 10;

int result = a - b;
```

The program may compile perfectly.

There is nothing syntactically wrong with it.

But if the programmer intended addition:

```cpp
int result = a + b;
```

then the problem is a **logic bug**.

The compiler cannot necessarily tell us that.

---

# 2. "The Computer Is Always Right"

A useful debugging mindset is:

> **Assume the computer is doing exactly what you told it to do.**

If the program produces an unexpected result, first investigate your own:

* code
* assumptions
* variable values
* memory
* control flow
* program state

rather than immediately assuming that the compiler or operating system is broken.

For example:

```cpp
int x = 10;

if (x > 20)
{
    std::cout << "x is greater than 20";
}
```

If the message doesn't appear, that's not necessarily a problem with C++.

The condition is simply false.

Debugging means investigating **why the program reached the state it did**.

---

# 3. Why Learn Debugging Early?

Debugging isn't just something you use when a large project breaks.

It's a way to understand what your program is actually doing.

Instead of only looking at:

```cpp
int x = 5;
int y = x + 10;
```

you can stop the program and inspect:

```text
x = 5
y = ?
```

Then execute the next instruction and see:

```text
x = 5
y = 15
```

This lets you observe the program's execution rather than simply guessing what happened.

---

# 4. Breakpoints

A **breakpoint** tells the debugger:

> "Pause the program when execution reaches this point."

For example:

```cpp
int main()
{
    int a = 10;     // breakpoint
    int b = 20;

    int result = a + b;
}
```

When execution reaches the breakpoint, the program pauses.

You can then inspect:

* variables
* memory
* the current execution location
* function calls
* call stack
* program state

The key idea is:

```text
Run program
    ↓
Reach breakpoint
    ↓
Pause
    ↓
Inspect state
    ↓
Continue / step
```

---

# 5. Breakpoints Must Correspond to Executable Code

A breakpoint needs to correspond to an instruction that can actually be executed.

For example:

```cpp
int main()
{
    // This is just a comment.

    int a = 10;
}
```

A breakpoint on:

```cpp
int a = 10;
```

makes sense.

A breakpoint on the comment doesn't represent an executable instruction.

---

# 6. Debug Build vs Release Build

This concept is important regardless of operating system.

A **debug build** is normally compiled with debugging information and fewer optimizations.

A **release build** is normally optimized for performance.

For learning/debugging, you generally want:

```text
Debug configuration
```

rather than an optimized release build.

Why?

Optimizations can:

* remove variables
* reorder instructions
* combine operations
* inline functions
* change the relationship between source code and machine instructions

This can make debugging confusing.

For example, you might write:

```cpp
int a = 10;
int b = 20;
int c = a + b;
```

but an optimizer may determine that some of those variables don't need to exist in memory in the same way you expect.

So:

> **Debug builds make the relationship between your source code and the running program easier to inspect.**

# 7. Linux Equivalent: GDB

The Cherno's video demonstrates **Visual Studio's debugger**, but on Linux the equivalent concept is commonly provided by **GDB (GNU Debugger)**.

You can compile a program with debugging information using:

```bash
g++ -g main.cpp -o program
```

Then start GDB:

```bash
gdb ./program
```

The important part is:

```bash
-g
```

This tells the compiler to include debugging information in the generated program.

The program can then be debugged using GDB.

---

# 8. Breakpoints on Linux/GDB

In GDB, you can set a breakpoint with:

```text
break main
```

or:

```text
break main.cpp:10
```

For example:

```text
(gdb) break main.cpp:10
```

Then run the program:

```text
(gdb) run
```

When execution reaches the breakpoint, GDB pauses.

You can then inspect the program.

---

# 9. Continue

The **Continue** operation means:

> Resume normal execution until another breakpoint is reached or the program terminates.

### Visual Studio

```text
F5
```

### GDB

```text
continue
```

or:

```text
c
```

Conceptually:

```text
Breakpoint
    ↓
Inspect
    ↓
Continue
    ↓
Next breakpoint
```

---

# 10. Step Over

**Step Over** executes the current line without entering a function called by that line.

Suppose:

```cpp
int main()
{
    int result = Add(10, 20);
}
```

If you step over:

```cpp
int result = Add(10, 20);
```

the debugger executes `Add()` and then stops at the next line in `main()`.

### Visual Studio

```text
F10
```

### GDB

```text
next
```

or:

```text
n
```

---

# 11. Step Into

**Step Into** enters a function being called on the current line.

For:

```cpp
int result = Add(10, 20);
```

Step Into takes you into:

```cpp
int Add(int a, int b)
{
    return a + b;
}
```

### Visual Studio

```text
F11
```

### GDB

```text
step
```

or:

```text
s
```

---

# 12. Step Out

**Step Out** finishes executing the current function and returns to its caller.

Suppose you're currently inside:

```cpp
int Add(int a, int b)
{
    return a + b;
}
```

Step Out executes the remainder of `Add()` and returns to the code that called it.

### Visual Studio

```text
Shift + F11
```

### GDB

```text
finish
```

---

# 13. Debugger Stepping — Quick Comparison

| Action         | Visual Studio | GDB/Linux        |
| -------------- | ------------- | ---------------- |
| Continue       | `F5`          | `continue` / `c` |
| Step Over      | `F10`         | `next` / `n`     |
| Step Into      | `F11`         | `step` / `s`     |
| Step Out       | `Shift + F11` | `finish`         |
| Set breakpoint | `F9`          | `break` / `b`    |

The **concepts are the same** even though the debugger interface is different.

# 14. The Yellow Arrow / Current Execution Line

In Visual Studio, the yellow arrow indicates the **current execution position**.

The important thing to remember is:

> **The highlighted/current line is the line about to execute.**

It has not necessarily executed yet.

For example:

```cpp
int a = 10;
int b = 20;
int c = a + b;
```

If the debugger is positioned on:

```cpp
int b = 20;
```

then the debugger is about to execute that statement.

`b` has not necessarily been assigned `20` yet.

This is a very important detail when stepping through code.

---

# 15. Inspecting Variables

One of the main purposes of a debugger is to inspect **program state**.

For example:

```cpp
int a = 10;
int b = 20;
int result = a + b;
```

When paused, you want to be able to ask:

```text
What is a?
What is b?
What is result?
```

The debugger can show:

```text
a      = 10
b      = 20
result = 30
```

This is much more useful than adding `std::cout` everywhere.

# 16. Visual Studio Variable Windows

The Cherno demonstrates Visual Studio's:

* **Autos**
* **Locals**
* **Watch**

windows.

### Autos

Shows variables that Visual Studio considers relevant to the current execution location.

### Locals

Shows local variables available in the current scope.

### Watch

Allows you to manually enter variables or expressions you want to monitor.

For example:

```text

b

```

The last one asks for the address of `a`.

# 17. Linux/GDB Variable Inspection

In GDB, the equivalent is generally done with:

```text
print variable
```

or:

```text
p variable
```

For example:

```text
(gdb) print a
$1 = 10
```

You can inspect multiple variables:

```text
(gdb) print a
(gdb) print b
(gdb) print result
```

You can also inspect expressions:

```text
(gdb) print a + b
```

and addresses:

```text
(gdb) print &a
```

# 18. Watching Variables in GDB

GDB also supports the idea of watching values.

For example:

```text
display a
```

will automatically display `a` when the debugger stops.

This is conceptually similar to putting a variable into a debugger's watch interface.

You can remove it with:

```text
undisplay
```

# 19. Changed Variables

Visual Studio can visually indicate variables whose values changed after stepping.

The Cherno points out the **red highlighting** used by Visual Studio for changed values.

For example:

Before stepping:

```text
a = 10
```

After executing:

```cpp
a = 20;
```

the debugger may show the changed value in red.

This is a **Visual Studio UI feature**, not a C++ feature.

The underlying debugging concept is:

> Track how program state changes as individual instructions execute.

# 20. Memory

A debugger can also let you inspect **raw memory**.

This is particularly useful in C++ because C++ gives you direct access to memory through things such as:

* pointers
* references
* arrays
* dynamic allocation
* addresses

Suppose:

```cpp
int a = 10;
```

The variable `a` exists somewhere in memory.

You can obtain its address using:

```cpp
&a
```

For example:

```text
0x7fffffffdabc
```

The exact address is not important.

The important idea is:

```text
a
↓
value stored somewhere in memory

&a
↓
address of that memory
```

---

# 21. Visual Studio Memory Window

The Cherno demonstrates:

```text
Debug
→ Windows
→ Memory
→ Memory 1
```

The Memory window displays raw memory.

It typically shows:

```text
Address       Hex bytes                ASCII
------------------------------------------------
0x...         0A 00 00 00              ....
```

The three conceptual sections are:

### Left

Memory address.

### Middle

Raw bytes represented in hexadecimal.

### Right

An ASCII interpretation of those bytes where applicable.

---

# 22. Linux/GDB Memory Examination

GDB can also examine raw memory.

The command is:

```text
x
```

For example:

```text
x/4xb &a
```

This means, roughly:

```text
x   → examine memory
4   → examine 4 units
x   → display in hexadecimal
b   → units are bytes
```

So if:

```cpp
int a = 10;
```

you can examine its memory using:

```text
(gdb) x/4xb &a
```

You can also use different formats and sizes.

For example:

```text
x/4xw &a
```

examines four words in hexadecimal.

The exact GDB syntax is less important for the core lesson than understanding that:

> **A debugger can let you inspect the actual bytes stored at a memory address.**

# 23. The Address-of Operator `&`

The `&` operator can be used to obtain the address of a variable.

Example:

```cpp
int a = 10;

std::cout << &a;
```

Conceptually:

```text
a
↓
10

&a
↓
address where 10 is stored
```

In a debugger, you can use this address to inspect the underlying memory.

In GDB:

```text
print &a
```

might produce something like:

```text
$1 = (int *) 0x7fffffffdabc
```

The exact address will vary between runs and systems.

# 24. Important: `0xCC` Is NOT a General C++ Rule

This is where the original Visual Studio video needs a Linux-specific qualification.

The Cherno discusses something like:

```text
CC CC CC CC
```

in debug builds.

This is associated with **Microsoft's Visual C++ / MSVC debug behavior**.

It should **not** be treated as:

> "C++ initializes uninitialized memory to `0xCC`."

It doesn't.

And it is not a universal Linux/GCC behavior.

---

# 25. Uninitialized Variables

Consider:

```cpp
int a;
```

`a` has been declared but has not been initialized.

For an automatic local variable like this, you should **not assume it contains zero**.

For example:

```cpp
int a;

std::cout << a;
```

Reading an uninitialized automatic variable can result in undefined behavior.

The important lesson is:

> **Do not rely on the contents of uninitialized memory.**

Always initialize variables when appropriate:

```cpp
int a = 0;
```

---

# 26. What Is `0xCC` Then?

With certain MSVC debug configurations, uninitialized stack memory can be filled with:

```text
CC
```

bytes.

So you might encounter something like:

```text
CC CC CC CC
```

or:

```text
0xCCCCCCCC
```

This is a **debugging aid provided by MSVC**, not a property of the C++ language.

The purpose is to make certain memory bugs more obvious during debugging.

### On Linux

With GCC/Clang, you should **not expect `0xCCCCCCCC`** simply because you compiled with debug information.

Your Linux toolchain has different debugging/runtime behavior.

So don't write a Linux note like:

> "Uninitialized variables contain `0xCC`."

That's incorrect.

Write:

> **MSVC debug builds may fill certain uninitialized stack memory with `0xCC`; this is an implementation/debug-runtime detail and is not a C++ or Linux rule.**

---

# 27. Debug Memory Patterns

The broader lesson behind `0xCC` is more useful than memorizing the number.

Debug runtimes can deliberately put recognizable patterns into memory to make bugs easier to identify.

For example:

```text
Normal memory:
    difficult to recognize

Debug-pattern memory:
    CC CC CC CC
```

If you encounter a recognizable pattern, it can provide a clue about what went wrong.

But:

> **Never build program logic around these debug memory patterns.**

They are diagnostic implementation details.

---

# 28. Guard Bytes / Stack Corruption

The Cherno also discusses debug builds placing additional diagnostic information around variables.

This can help detect things such as **buffer overflows** and **stack corruption**.

For example, imagine:

```cpp
char buffer[8];
```

and accidentally writing beyond its bounds:

```cpp
buffer[20] = 'A';
```

That can overwrite memory that doesn't belong to the array.

A debug runtime can sometimes place recognizable data around memory regions and check whether that data was overwritten.

Conceptually:

```text
[ guard ][ buffer ][ guard ]
           ↓
       overflow
           ↓
[ guard ][ buffer ][XXXXXX]
                         ↑
                    corruption
```

If the guard region is changed unexpectedly, the debugger/runtime can report that the surrounding memory has been corrupted.

---

# 29. Debug vs Release — Memory Diagnostics

Debug configurations may add:

* diagnostic checks
* debugging information
* recognizable memory patterns
* additional runtime checks
* less aggressive optimization

Release configurations generally prioritize:

* performance
* smaller/faster binaries
* optimization

Therefore, debug behavior can differ significantly from release behavior.

Again, the exact mechanisms depend on the compiler, runtime, operating system, and build configuration.

# 30. Linux Perspective on Debug Builds

On Linux, a typical GCC compilation for debugging might be:

```bash
g++ -g -O0 main.cpp -o program
```

Here:

```text
-g
```

adds debugging information.

And:

```text
-O0
```

disables optimization.

For a multi-file project:

```bash
g++ -g -O0 main.cpp Log.cpp -o program
```

Then:

```bash
gdb ./program
```

You can debug the resulting program.

### Important distinction

`-g` and `-O0` do different things:

```text
-g
↓
Include debugging information

-O0
↓
Don't optimize the code
```

You can technically have debug information with optimization enabled, but debugging optimized code can be substantially harder to follow.

# 31. A Simple Linux Debugging Example

Consider:

```cpp
#include <iostream>

int Add(int a, int b)
{
    int result = a + b;
    return result;
}

int main()
{
    int x = 10;
    int y = 20;

    int result = Add(x, y);

    std::cout << result << '\n';
}
```

Compile:

```bash
g++ -g -O0 main.cpp -o program
```

Start GDB:

```bash
gdb ./program
```

Set a breakpoint:

```text
(gdb) break main
```

Run:

```text
(gdb) run
```

Step:

```text
(gdb) next
```

Inspect:

```text
(gdb) print x
(gdb) print y
(gdb) print result
```

Enter the function:

```text
(gdb) step
```

Finish the function:

```text
(gdb) finish
```

Continue:

```text
(gdb) continue
```

This gives you essentially the same **debugging workflow** demonstrated in the Visual Studio video.

# 32. Core Debugging Workflow

The important workflow to take away from the video is:

```text
1. Identify suspicious code
        ↓
2. Set breakpoint
        ↓
3. Run program
        ↓
4. Program pauses
        ↓
5. Inspect variables/state
        ↓
6. Step through execution
        ↓
7. Observe what changes
        ↓
8. Find where actual behavior diverges
           from expected behavior
        ↓
9. Fix the code
```

The debugger isn't merely a tool for stopping crashes.

It's a tool for **observing program execution**.
